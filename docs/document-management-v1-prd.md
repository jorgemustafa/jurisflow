# Document Management v1 PRD

## Problem Statement

Magistrum needs a simple way to organize client and case documents without turning document storage into a complex workflow too early.

Law offices need to quickly attach contracts, IDs, petitions, proofs, receipts, and other files to the right client or case. The first version should prioritize reliable metadata, clear ownership, and retrieval by client/case before adding advanced storage, preview, OCR, templates, or permissions.

## Solution

Document Management v1 stores document metadata in the database and keeps the physical file storage strategy explicit and replaceable.

Every document belongs to one client. A document can optionally belong to one case, but if a case is provided, that case must belong to the same client. This keeps the root ownership simple while still supporting case-specific organization.

V1 should support uploading a file, listing documents by client, listing documents by case, and basic metadata validation. Physical delete is out of scope; documents should be soft-deleted or archived when that workflow is introduced.

## User Stories

1. As an office user, I want to upload a document for a client, so that client files stay centralized.
2. As an office user, I want to optionally link a document to a case, so that case-specific files are easy to find.
3. As an office user, I want a case-linked document to still belong to the client, so that all client documents remain visible together.
4. As an office user, I want document names to be clear and required, so that files can be recognized without opening them.
5. As an office user, I want the system to store file metadata, so that documents can be listed and filtered later.
6. As an office user, I want to list all documents for a client, so that I can review the full client file.
7. As an office user, I want to list all documents for a case, so that I can review the case file.
8. As an office user, I want invalid or unsupported files to be rejected, so that storage stays predictable.

## Implementation Decisions

- Document Management v1 is metadata-first with simple upload support.
- Every document must belong to a client.
- A document can optionally belong to a case.
- If `caseId` is provided, the case must belong to the same client.
- Document name is required and should be trimmed.
- File path or object key is required and should be generated by the system, not trusted from the client.
- MIME type is required and should come from the upload handling layer.
- Original file name should be stored when upload is implemented.
- File size should be stored when upload is implemented.
- Physical file storage should be hidden behind a storage service boundary.
- Local filesystem storage is acceptable for development.
- Production storage should be replaceable with object storage later.
- Physical document deletion is out of scope for v1.
- Versioning is out of scope for v1.
- OCR, full-text search, preview generation, and templates are out of scope for v1.

## Recommended Storage Strategy

Start with a storage service interface in the API:

```txt
documents.storage.ts
  save(input) -> stored file metadata
  remove(key) -> cleanup helper for failed metadata writes or future delete/archive flows
```

The repository should only persist metadata. It should not know whether files are stored locally, in S3, or elsewhere.

For local development, store files under a configured local directory outside source code, for example:

```txt
MAGISTRUM_STORAGE_DIR=./storage
```

Do not commit uploaded files.

## API Shape

Recommended endpoints:

```txt
POST   /documents
GET    /documents?clientId=<id>
GET    /documents?caseId=<id>
GET    /documents/:id
```

Upload should use `multipart/form-data` when file upload is implemented.

Required create fields:

- `clientId`
- `name`
- `file`

Optional create fields:

- `caseId`

Metadata generated by the API:

- `path` or storage key
- `mimeType`
- `originalName`
- `sizeBytes`

## Data Model Notes

The current baseline `Document` model has:

```txt
id
clientId
caseId
name
path
mimeType
createdAt
updatedAt
```

Before upload implementation, consider adding:

```txt
originalName String
sizeBytes    Int
```

Future archive/delete support can add:

```txt
status       DocumentStatus
archivedAt   DateTime?
```

## Testing Decisions

Tests should cover business behavior:

- Create document metadata for a client.
- Create document metadata linked to a case from the same client.
- Reject document metadata when the case belongs to another client.
- Reject missing or blank document name.
- Reject missing file metadata.
- List documents by client.
- List documents by case.
- Keep storage cleanup behavior covered when metadata persistence fails after file save.

Avoid tests that only mock a storage service call without asserting document ownership, metadata, or cleanup rules.

## Out of Scope

- Authentication and authorization.
- Physical delete.
- Document versioning.
- OCR and full-text search.
- Document preview generation.
- Document templates.
- E-signatures.
- External cloud storage integration as the first implementation.
- Advanced document categories/tags.
