# Data Model Decisions

This document records current database model decisions. `Client`, the minimal `User` model, the base `Case` model, and `Payment` are approved for their first implementation pass. `Document` is a baseline model and can change when its business rules are defined.

## Enums

### ClientType

- `INDIVIDUAL`
- `COMPANY`

Use for `Client.type`. Required.

### ClientStatus

- `ACTIVE`
- `INACTIVE`

Use for `Client.status`. New clients default to `ACTIVE`. Inactive clients stay editable and can be reactivated.

### CaseStatus

- `ACTIVE`
- `ON_HOLD`
- `CLOSED`
- `CANCELED`

Use for the macro operational state of a case.

### CaseType

- `JUDICIAL`
- `EXTRAJUDICIAL`

Use for `Case.caseType`. Required. New cases default to `JUDICIAL`.

### CaseStage

- `INITIAL`
- `HEARING_SCHEDULED`
- `WAITING_DECISION`
- `APPEAL`
- `ENFORCEMENT`

Use for the current legal stage when known. Optional.

### LegalArea

- `CIVIL`
- `LABOR`
- `FAMILY`
- `CRIMINAL`
- `TAX`
- `CONSUMER`
- `BUSINESS`
- `SOCIAL_SECURITY`
- `OTHER`

Use for `Case.legalArea`. Optional. The database has no default; the case creation UI can preselect `CRIMINAL` for the initial criminal law office use case.

### CaseTimelineEventType

- `NOTE`
- `HEARING`
- `PETITION`
- `DECISION`
- `STATUS_CHANGE`
- `OTHER`

Use for manual case timeline events. Required.

### CaseDeadlineStatus

- `PENDING`
- `DONE`
- `CANCELED`

Use for case deadline completion state. Required. Overdue and due-soon are computed alert levels, not stored statuses.

### UserRole

- `ADMIN`
- `LAWYER`
- `ASSISTANT`

Use for `User.role`. Defaults to `LAWYER`.

### UserStatus

- `ACTIVE`
- `INACTIVE`

Use for `User.status`. Defaults to `ACTIVE`.

### PaymentStatus

- `PENDING`
- `PAID`
- `CANCELED`

Do not store overdue as a status. Overdue is computed from pending payments whose due date is in the past.

### PaymentSource

- `GENERATED`
- `MANUAL`

Use to distinguish generated case installments from manually created payments.

### PaymentMethod

- `PIX`
- `CASH`
- `BANK_TRANSFER`
- `CREDIT_CARD`
- `DEBIT_CARD`
- `BOLETO`
- `OTHER`

Use when a payment is marked as paid. Nullable in the database; UI defaults to PIX.

## Client

Approved for Client Management v1.

| Field       | Type           | Required | Rules                                                                    |
| ----------- | -------------- | -------- | ------------------------------------------------------------------------ |
| `id`        | UUID string    | yes      | Primary key generated by the database layer.                             |
| `type`      | `ClientType`   | yes      | Individual or company.                                                   |
| `status`    | `ClientStatus` | yes      | Defaults to `ACTIVE`.                                                    |
| `name`      | string         | yes      | Full name for individuals; company/legal name for companies.             |
| `document`  | string         | no       | CPF/CNPJ, digits only, unique when present, max 14 chars.                |
| `email`     | string         | no       | Valid email when present, saved trimmed and lowercase, not unique.       |
| `phone`     | string         | no       | Brazilian phone, digits only, 10 or 11 digits, not unique, max 11 chars. |
| `address`   | string         | no       | Free text in v1.                                                         |
| `notes`     | string         | no       | Free text in v1.                                                         |
| `createdAt` | datetime       | yes      | System managed.                                                          |
| `updatedAt` | datetime       | yes      | System managed.                                                          |

### Client Indexes

- Unique index on `document`.
- Index on `status`.
- Index on `type`.
- Composite index on `status` and `type`.

### Client Rules Not Enforced By The Database

- CPF must be valid when `type` is `INDIVIDUAL` and `document` is present.
- CNPJ must be valid when `type` is `COMPANY` and `document` is present.
- Type can change only if the existing document remains valid for the new type or the document is removed/changed.
- Duplicate names are allowed.
- Inactive clients are excluded from default listing but remain viewable and editable.
- Creating future cases for inactive clients should require reactivation.

## User

Approved as a minimal model required before Case Management so cases can reference the responsible lawyer. Full authentication can be implemented later.

| Field          | Type         | Required | Rules                                              |
| -------------- | ------------ | -------- | -------------------------------------------------- |
| `id`           | UUID string  | yes      | Primary key generated by the database layer.       |
| `name`         | string       | yes      | User display name.                                 |
| `email`        | string       | yes      | Unique login/contact email.                        |
| `passwordHash` | string       | no       | Optional until full authentication is implemented. |
| `role`         | `UserRole`   | yes      | Defaults to `LAWYER`.                              |
| `status`       | `UserStatus` | yes      | Defaults to `ACTIVE`.                              |
| `createdAt`    | datetime     | yes      | System managed.                                    |
| `updatedAt`    | datetime     | yes      | System managed.                                    |

### User Rules Not Enforced By The Database

- Only active users can be assigned as responsible for a case.
- Only users with `LAWYER` or `ADMIN` role can be the main responsible user for a case.
- `ASSISTANT` users can exist, but cannot be the primary responsible lawyer.

## Case

Approved as the base Case Management model.

| Field                 | Type         | Required | Rules                                                           |
| --------------------- | ------------ | -------- | --------------------------------------------------------------- |
| `id`                  | UUID string  | yes      | Primary key generated by the database layer.                    |
| `clientId`            | UUID string  | yes      | Required relation to `Client`.                                  |
| `responsibleUserId`   | UUID string  | no       | Optional relation to the main responsible lawyer.               |
| `caseType`            | `CaseType`   | yes      | Defaults to `JUDICIAL`.                                         |
| `title`               | string       | yes      | Human-readable case title.                                      |
| `cnjNumber`           | string       | no       | CNJ number, unique when present, valid only for judicial cases. |
| `status`              | `CaseStatus` | yes      | Defaults to `ACTIVE`.                                           |
| `stage`               | `CaseStage`  | no       | Current legal stage when known.                                 |
| `legalArea`           | `LegalArea`  | no       | Optional legal area; UI can preselect `CRIMINAL`.               |
| `opposingParty`       | string       | no       | Free-text opposing party.                                       |
| `court`               | string       | no       | Free-text court or tribunal.                                    |
| `jurisdiction`        | string       | no       | Free-text comarca, foro, or section.                            |
| `division`            | string       | no       | Free-text vara, turma, or chamber.                              |
| `description`         | string       | no       | Free text summary.                                              |
| `openedAt`            | datetime     | no       | Real-world case opening date, can be before system creation.    |
| `closedAt`            | datetime     | no       | Operational close/cancel date.                                  |
| `totalFeeAmountCents` | integer      | yes      | Legally agreed case fee. Immutable after case creation.         |
| `createdAt`           | datetime     | yes      | System managed.                                                 |
| `updatedAt`           | datetime     | yes      | System managed.                                                 |

### Case Relationship Rules

- A client can have many cases.
- A case belongs to exactly one client.
- Creating a case for an inactive client should require reactivating the client first.
- A case can have one optional main responsible user.
- A responsible user must be active and have `LAWYER` or `ADMIN` role.
- Multiple case members are out of scope for v1.

### Case Rules Not Enforced By The Database

- `cnjNumber` is optional for judicial cases.
- `cnjNumber` is prohibited for extrajudicial cases.
- `cnjNumber` must be valid and unique when present.
- Empty optional classifications such as `stage` and `legalArea` are omitted on creation and cleared with `null` on update.
- Importing a judicial case by CNJ is blocked when another case already has the same `cnjNumber`.
- Imported judicial cases are created only after a user manually selects an active client.
- DataJud import is an assistive public-data workflow; users must review the preview before confirming the case.
- `clientId` cannot change after case creation because the financial agreement and generated payments are legally bound to that client.
- Closing or canceling a case is blocked when there is pending finance linked to that case.
- Closed or canceled cases remain editable for corrections.
- Closing or canceling a case does not automatically inactivate the client.
- Finance data is required for manual and imported case creation.
- Case, paid entry, generated installments, and imported movements are persisted atomically per case.
- `totalFeeAmountCents` cannot be edited after creation. Renegotiation is outside v1.

### Case Import Batch Rules

- Import batch items keep system-managed creation and update timestamps for auditability.
- Batch items are returned in creation order so the review keeps the submitted CNJ order.

### Case Indexes

- Unique index on `cnjNumber`.
- Index on `clientId`.
- Index on `responsibleUserId`.
- Index on `status`.
- Index on `caseType`.
- Index on `stage`.
- Index on `legalArea`.

## Case Timeline Event

Approved for Case Management v1.

| Field             | Type                    | Required | Rules                                                                           |
| ----------------- | ----------------------- | -------- | ------------------------------------------------------------------------------- |
| `id`              | UUID string             | yes      | Primary key generated by the database layer.                                    |
| `caseId`          | UUID string             | yes      | Required relation to `Case`.                                                    |
| `createdByUserId` | UUID string             | no       | Authenticated user who created the event when available.                        |
| `externalSource`  | string                  | no       | External source identifier when the event is imported.                          |
| `externalId`      | string                  | no       | External movement identifier when available.                                    |
| `sourceHash`      | string                  | no       | Deterministic hash used to avoid duplicate imported movements in the same case. |
| `type`            | `CaseTimelineEventType` | yes      | Classifies the timeline entry.                                                  |
| `title`           | string                  | yes      | Short human-readable event title.                                               |
| `description`     | string                  | no       | Free-text details.                                                              |
| `occurredAt`      | datetime                | yes      | Real-world event date; defaults to creation time when omitted.                  |
| `createdAt`       | datetime                | yes      | System managed.                                                                 |
| `updatedAt`       | datetime                | yes      | System managed.                                                                 |

### Case Timeline Event Relationship Rules

- A case can have many timeline events.
- A timeline event belongs to exactly one case.
- Timeline events are append-only in v1; editing and deletion are out of scope.
- Timeline events can be added to active, paused, closed, or canceled cases for operational history.
- The creator relation is kept nullable so events remain available if user attribution is unavailable.
- Imported DataJud movements are stored as timeline events with `externalSource = datajud`.
- Imported movements are deduplicated by `caseId` and `sourceHash`.
- Manual timeline events keep external source fields empty.

### Case Timeline Event Indexes

- Composite index on `caseId` and `occurredAt`.
- Unique index on `caseId` and `sourceHash`.
- Index on `createdByUserId`.
- Index on `externalSource`.
- Index on `type`.

## Case Deadline

Approved for Case Management v1.

| Field         | Type                 | Required | Rules                                                 |
| ------------- | -------------------- | -------- | ----------------------------------------------------- |
| `id`          | UUID string          | yes      | Primary key generated by the database layer.          |
| `caseId`      | UUID string          | yes      | Required relation to `Case`.                          |
| `title`       | string               | yes      | Short description of the deadline.                    |
| `description` | string               | no       | Free-text details.                                    |
| `dueAt`       | datetime             | yes      | Deadline due date.                                    |
| `status`      | `CaseDeadlineStatus` | yes      | Defaults to `PENDING`.                                |
| `completedAt` | datetime             | no       | Set when status changes to `DONE`; cleared otherwise. |
| `createdAt`   | datetime             | yes      | System managed.                                       |
| `updatedAt`   | datetime             | yes      | System managed.                                       |

### Case Deadline Rules

- A case can have many deadlines.
- A deadline belongs to exactly one case.
- Overdue is computed as pending with `dueAt` before today.
- Due-soon is computed as pending with `dueAt` within the selected alert window.
- Done and canceled deadlines do not produce alerts.
- Deadline `title`, `description`, and `dueAt` can be edited for correction without changing `status` or `completedAt`.
- Deadline status can be manually changed between pending, done, and canceled. Changing to done sets `completedAt`; changing to pending or canceled clears `completedAt`.

### Case Deadline Indexes

- Composite index on `caseId` and `dueAt`.
- Composite index on `status` and `dueAt`.

## Payment

Approved for Finance v1.

| Field               | Type            | Required | Rules                                                                           |
| ------------------- | --------------- | -------- | ------------------------------------------------------------------------------- |
| `id`                | UUID string     | yes      | Primary key generated by the database layer.                                    |
| `clientId`          | UUID string     | yes      | Required relation to `Client`.                                                  |
| `caseId`            | UUID string     | no       | Optional relation to `Case` when a payment belongs to a case.                   |
| `paymentScheduleId` | UUID string     | no       | Shared id for generated installments in one schedule. Null for manual payments. |
| `source`            | `PaymentSource` | yes      | `GENERATED` or `MANUAL`. Defaults to `MANUAL`.                                  |
| `description`       | string          | yes      | Human-readable payment description.                                             |
| `amountCents`       | integer         | yes      | Store money as integer cents.                                                   |
| `dueDate`           | datetime        | yes      | Payment due date.                                                               |
| `paidAt`            | datetime        | no       | Filled when payment is paid.                                                    |
| `paymentMethod`     | `PaymentMethod` | no       | Required by API when marking as paid. UI defaults to PIX.                       |
| `status`            | `PaymentStatus` | yes      | Defaults to `PENDING`.                                                          |
| `installmentNumber` | integer         | yes      | One full payment uses `1`.                                                      |
| `installmentTotal`  | integer         | yes      | One full payment uses `1`.                                                      |
| `notes`             | string          | no       | General finance observation.                                                    |
| `canceledAt`        | datetime        | no       | Set automatically when canceled.                                                |
| `cancelReason`      | string          | no       | Required by API when canceling.                                                 |
| `createdAt`         | datetime        | yes      | System managed.                                                                 |
| `updatedAt`         | datetime        | yes      | System managed.                                                                 |

### Payment Relationship Rules

- A client can have many payments.
- A payment belongs to one client.
- A payment can optionally belong to one case.
- If a payment has `caseId`, the case must belong to the same client.
- Client-only payments are allowed.
- Pending finance linked to a case blocks closing or canceling that case.
- Generated payments are grouped by `paymentScheduleId`.
- A case can have at most one generated schedule in v1.
- A generated entry uses `installmentNumber = 0`; future installments use `1/N` through `N/N`.
- No physical delete in v1. Use `CANCELED`.

### Payment Rules Not Enforced By The Database

- Overdue is computed as `PENDING` with `dueDate` before today.
- No partial payments.
- Marking a payment as paid requires `paidAt` and `paymentMethod`.
- UI defaults `paymentMethod` to PIX.
- Canceling a payment requires `cancelReason`.
- Generated amount, due date, description, numbering, schedule, and cancellation are locked; only receipt and notes are allowed.
- Pending manual payment can edit amount, due date, description, and notes.
- Pending generated payment can edit due date, description, and notes.
- Paid payment can only correct `paidAt` or be canceled.
- Canceled payment can only edit `cancelReason` and `notes`.
- Canceled payments do not count as receivable or paid revenue.
- Pending overdue payments remain visible in later month scopes without changing `dueDate`; `dueDate` is their immutable competence reference.
- A pending payment is overdue only when `dueDate` is before today, regardless of the month currently selected in the finance UI.
- A late receipt is also visible in its `paidAt` month with the original competence.

## Document

Approved as a baseline for Document Management v1. Upload implementation should consider adding `originalName` and `sizeBytes` before the first file upload endpoint.

| Field       | Type        | Required | Rules                                        |
| ----------- | ----------- | -------- | -------------------------------------------- |
| `id`        | UUID string | yes      | Primary key generated by the database layer. |
| `clientId`  | UUID string | yes      | Required relation to `Client`.               |
| `caseId`    | UUID string | no       | Optional relation to `Case`.                 |
| `name`      | string      | yes      | Human-readable document name.                |
| `path`      | string      | yes      | Storage path or object key.                  |
| `mimeType`  | string      | yes      | File MIME type.                              |
| `createdAt` | datetime    | yes      | System managed.                              |
| `updatedAt` | datetime    | yes      | System managed.                              |

### Document Relationship Rules

- A client can have many documents.
- A document belongs to one client.
- A document can optionally belong to one case.
- If a document has `caseId`, the case must belong to the same client.
- Document metadata registration validates `name`, storage `path`, and MIME type before persistence.
- Upload v1 stores metadata and storage path only; binary transfer is still behind the storage service boundary.
- File storage is hidden behind a storage service boundary.
- Repository code persists metadata only.
- Physical delete, versioning, OCR, preview generation, and templates are out of scope for v1.

### Document Indexes

- Index on `clientId`.
- Index on `caseId`.
- Index on `mimeType`.
